# Synchronous P3 / pinned / managed-UVA phase comparison

This experiment compares the current synchronous P3 path with vLLM pinned
copy-on-forward and the project's custom managed-UVA remote-read path.  It
measures prefill and decode as separate, scheduler-validated engine steps.

The historical reproduction report was superseded on 2026-08-23. Use this
implementation entry point together with
[`../../docs/eurosys_moe_offload_evaluation_plan.md`](../../docs/eurosys_moe_offload_evaluation_plan.md).

## Equal weight contract

Every arm uses the same Qwen3-30B-A3B-FP8 main expert weights:

- layers 0 through 3;
- all 128 packed experts in each selected layer;
- `w13_weight` and `w2_weight` only;
- 576 MiB per layer and 2.25 GiB total;
- 1,152 logical 512-KiB regions per layer.

The full packed tensors are intentional.  The existing vLLM pinned parameter
offloader cannot select twelve individual expert slices inside a packed Qwen
tensor.  A sparse-12 P3/pinned comparison would therefore move different
bytes.  P3 and pinned copy the complete 2.25-GiB selection on every forward;
managed-UVA maps the same selection, but PCIe traffic remains routing-demand
dependent.

The three process-isolated arms are:

- `P`: synchronous fenced P3 ioctl cmd96, registered 512-KiB plans, 64-KiB
  PTEs, copy-run and metadata caches, dual bank, CUDA compute/completion
  fences, O(1) bank commit, compact trace, and epoch validation;
- `C`: vLLM exact-name pinned-host `copy_` on forward, nonblocking and without
  a forced per-layer host synchronization;
- `U`: custom managed-UVA `remote_read` placement for exactly the same expert
  regions.

## Phase measurement contract

The default frozen fixture gives 314 prompt tokens at batch 1 and 1,217 prompt
tokens at batch 4.  For every batch and repeat, the in-process V1 EngineCore
runner performs:

1. exactly one scheduler step containing all new prompt tokens and no cached,
   resumed, speculative, encoder, or preempted request work;
2. five unmeasured cached decode warmup steps;
3. sixteen measured cached decode steps, each scheduling exactly one token per
   request;
4. a final output/hash check after the timing window.

Every engine step is bracketed by `torch.cuda.synchronize()`.  Therefore the
reported values are ready-to-use GPU wall times, not asynchronous host-submit
times.

Primary metrics are kept separate:

- `prefill_step_ms`: one complete synchronized prefill engine step;
- `decode_step_ms`: synchronized cached one-token-per-request decode step;
- `cycle_e2e_ms`: the whole request cycle (one prefill plus all warmup and
  measured decode steps), reported separately so it cannot contaminate either
  phase metric;
- standard vLLM request TTFT, average TPOT, and request latency, retained as
  secondary serving metrics and never substituted for the strict step times;
- prompt/decode tokens per second derived from the process-level phase median.

One process performs one conditioning repeat and three measured repeats for
each batch.  The independent statistical sample is the process median, not an
individual request or decode step.  The default process order is the balanced
Latin sequence `PCU CUP UPC`; every three-process block contains all arms, and
the batch scan direction alternates by block.

No NVML query, subprocess, trace inspection, result serialization, or file
write from the benchmark runner occurs inside the phase loop.  P3's compact
production trace is still generated by the mechanism itself and is included
in the measured cost.

## Static validation

This does not initialize CUDA or change a kernel module:

```bash
cd /home/ubuntu/nvidia-uvm-gpu
bash experiments/vllm_p3_pinned_uva_phase_compare/run_phase_compare.sh \
  static-preflight
```

It checks that P3 uses synchronous cmd96, rejects remnants of cmd97/cmd98,
checks the registered P3 and custom remote-read integrations, compiles the
runner/verifier, and executes the unit tests.

## Runtime

The self-restoring module-cycle wrapper is the normal entry point:

```bash
cd /home/ubuntu/nvidia-uvm-gpu
RUN_ROOT=/home/ubuntu/nvidia-uvm-gpu/experiments/\
vllm_p3_pinned_uva_phase_compare/artifacts/$(date -u +%Y%m%dT%H%M%SZ)_formal \
ORDER=PCUCUPUPC \
BATCH_SIZES=1,4 \
bash experiments/vllm_p3_pinned_uva_phase_compare/run_with_module_cycle.sh
```

The wrapper loads the custom UVM with the complete synchronous P3 parameter
set, forces epoch validation on, runs all arms, restores stock UVM on every
exit path, and restores exporter services.  The GPU must begin and end at
exactly 0 MiB with no compute process.

For a one-process-per-arm qualification smoke (not a formal performance
sample), set `ORDER=PCU`.  `MODEL`, `EVAL_FIXTURE`, `GPU_INDEX`, `CPUSET`,
`CPU_THREADS`, `TIMEOUT_SEC`, `CONDITIONING_REPEATS`,
`MEASUREMENT_REPEATS`, `WARMUP_DECODE_STEPS`, and
`MEASURED_DECODE_STEPS` are overrideable.  The verifier requires batches 1
and 4, at least one conditioning repeat, at least three measurement repeats,
and at least one decode warmup step.

### Clock control

The runner records GPU P-state/current SM and memory clocks before and after
every process, plus CPU topology/governors.  It deliberately does not call
NVML inside the hot loop.  For the strongest repeatability, lock supported GPU
clocks externally before invoking the wrapper and reset them afterward; for
example, use the deployment-approved `nvidia-smi -lgc ...` setting and later
`nvidia-smi -rgc`.  If clocks cannot be locked, retain the default conditioning
repeat and balanced process order, and treat a P3 frequency-ramp/bimodal run
as invalid rather than mixing cold and steady samples.

## Verification and artifacts

Each run root contains:

- the exact plan and pinned parameter list plus SHA-256 hashes;
- command/environment, process return code, GPU snapshots, resource usage,
  and before/after UVM counters for every arm;
- strict per-cycle scheduler records and separate prefill/decode/E2E timings;
- P3 compact transition trace;
- pinned allocation manifest and managed-UVA placement manifest;
- `verification.json`, whose comparisons use independent process medians and
  paired three-process blocks.

The verifier requires:

- identical frozen prompts and output-token hashes in all arms;
- exact pinned parameter names, pinned CPU backing, and 2.25-GiB allocation;
- exact custom managed-UVA region placement and byte coverage;
- every P3 transition to use registered cmd96 execution, one shared copy push,
  64-KiB PTE coverage, accepted compute fence, signaled completion, enqueued
  stream wait, O(1) bank commit, and cache hits;
- zero P3 fallback, error, conflict, or poisoned session;
- no P3 plan execution in pinned or managed-UVA arms.

Re-run verification without the GPU:

```bash
bash experiments/vllm_p3_pinned_uva_phase_compare/run_phase_compare.sh \
  verify /absolute/path/to/run_root
```

## Existing-data boundary

Earlier artifacts do not replace this experiment:

- `vllm_prefill_p3_steady_compare` is a fair 2.25-GiB prefill framework, but
  its balanced six-process artifact predates O(1) bank commit/compact
  trace/epoch validation; the optimized post-rollback result has only one
  process per arm.
- `vllm_copy_decode_crossover` supplies the strict decode-step method, but its
  `uva` arm is generic native UVA, uses 62 parameters/2.1347 GiB, and has no
  P3 arm.
- `vllm_prefill_p3_decode_remote` proves sparse P3-to-remote cutover
  correctness, but uses sparse 48x12 placement, one process, and no pinned arm.

This benchmark is still intentionally limited to eager, single-GPU,
single-process execution.  It does not qualify CUDA Graph, multi-GPU
communication, or sparse packed-tensor pinned slicing.
